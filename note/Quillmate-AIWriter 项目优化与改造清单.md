# Quillmate-AIWriter 项目优化与改造清单

项目地址：https://github.com/L-jiemoo/Quillmate-AIWriter

## 一、总体改造目标

将 Quillmate-AIWriter 从基础的 AI 小说生成工具，升级为具备可靠数据管理、长篇剧情记忆、多 Agent 协作、章节版本管理和自动发布能力的 AI 小说创作平台。

改造原则：

1. 优先修复现有代码中的问题，不要盲目增加新功能。
2. 尽可能保留现有功能，避免破坏已有工作流程。
3. 先完成底层架构改造，再升级 AI 创作能力。
4. 所有修改必须经过测试，不能只保证代码能够编译。
5. 不允许为了方便而删除现有功能或简化原有业务逻辑。

## 二、第一阶段：核心代码与数据安全（P0）

### 1. 数据读取与写入

- 

  修复 JSON 读取异常时直接返回默认空数据的问题。

- 

  区分文件不存在、文件损坏和文件读取异常。

- 

  增加文件原子写入机制，避免程序异常导致数据损坏。

- 

  重要文件写入前自动备份。

- 

  禁止在读取失败时使用默认数据覆盖原有文件。

- 

  增加数据完整性检查。

### 2. 任务调度与并发控制

- 

  修复任务检查与任务创建之间的并发竞争问题。

- 

  增加项目级任务锁。

- 

  同一个项目不允许执行相互冲突的写作任务。

- 

  增加任务超时处理。

- 

  增加任务取消功能。

- 

  增加失败任务重试机制。

- 

  记录每个任务的开始时间、结束时间、状态和错误信息。

- 

  服务重启后能够识别未完成任务，并提供恢复或重新执行机制。

### 3. 事实台账与章节审校

- 

  修复事实抽取失败后仍可能通过章节审校的问题。

- 

  事实抽取失败时禁止自动更新正式台账。

- 

  台账重建采用临时数据，全部成功后再替换正式数据。

- 

  任意章节处理失败时保留原有台账。

- 

  增加事实冲突检测。

- 

  增加事实来源追踪，记录每条事实来自哪个章节。

- 

  增加人物状态、地点、物品和时间线的变化记录。

### 4. 架构生成逻辑

- 

  修复架构生成过程中部分数据保存成功、部分数据生成失败的问题。

- 

  架构、大纲、人物卡生成完成并通过校验后再正式提交。

- 

  增加章节编号重复检查。

- 

  增加章节编号连续性检查。

- 

  增加空标题、空摘要和异常章节数据检查。

- 

  增加统一的大纲数据验证函数。

## 三、第二阶段：SQLite 数据库改造（P0）

将目前以 JSON 和 Markdown 文件为主的数据管理方式升级为 SQLite + Markdown 混合存储架构。

注意：不需要把所有小说正文都存入数据库。

### 1. 数据库设计

建议增加以下数据表：

- 

  projects：作品信息。

- 

  chapters：章节信息及状态。

- 

  characters：人物信息。

- 

  canon_facts：小说事实台账。

- 

  jobs：后台任务。

- 

  job_logs：任务执行日志。

- 

  chapter_versions：章节历史版本。

- 

  reviews：章节审校记录。

- 

  plot_events：剧情事件。

- 

  foreshadows：伏笔管理。

- 

  model_configs：模型配置元数据。

### 2. 数据库基础能力

- 

  接入 SQLite。

- 

  建立统一数据库访问层。

- 

  增加数据库版本迁移机制。

- 

  增加数据库事务。

- 

  增加合理的外键和索引。

- 

  增加数据库备份和恢复。

- 

  增加旧 JSON 数据迁移工具。

- 

  数据迁移完成后进行完整性验证。

- 

  保留 Markdown 正文文件的导入、导出能力。

### 3. 章节版本管理

- 

  每次 AI 生成后自动保存版本。

- 

  每次人工修改后支持保存版本。

- 

  支持查看历史版本。

- 

  支持版本差异对比。

- 

  支持恢复任意历史版本。

- 

  恢复旧版本时不能直接删除其他历史记录。

## 四、第三阶段：AI 小说创作能力升级（P1）

### 1. 剧情事件管理

增加 plot_events 剧情事件系统。

每个事件至少包含：

- 事件 ID。
- 所属章节。
- 事件名称。
- 事件描述。
- 参与人物。
- 发生地点。
- 事件前状态。
- 事件后状态。
- 事件造成的后续影响。
- 相关伏笔。

要求：

- 

  每章完成后自动提取关键剧情事件。

- 

  记录剧情事件之间的关联。

- 

  支持查询某个人物参与过的所有事件。

- 

  支持根据章节查询剧情发展。

- 

  写作时将相关历史事件提供给 AI。

### 2. 人物状态追踪

- 

  追踪人物生死状态。

- 

  追踪人物所在地点。

- 

  追踪人物当前目标。

- 

  追踪人物性格及心理变化。

- 

  追踪人物之间的关系变化。

- 

  追踪人物已知秘密和未知秘密。

- 

  追踪人物持有的物品。

- 

  防止人物出现不符合已有剧情的行为。

### 3. 伏笔管理

- 

  自动提取章节中的潜在伏笔。

- 

  记录伏笔首次出现章节。

- 

  记录伏笔涉及的人物和事件。

- 

  记录伏笔状态：未回收、已回收、废弃。

- 

  提醒作者长期未回收的伏笔。

- 

  写作时检查是否需要推进已有伏笔。

- 

  防止 AI 擅自将未确认的伏笔判定为已经回收。

### 4. 长篇小说记忆系统

将目前主要依赖最近章节摘要的记忆机制升级为分层记忆。

第一层：全书记忆

- 世界观。
- 核心设定。
- 全书主线。
- 核心人物。
- 重要秘密。

第二层：分卷记忆

- 分卷大纲。
- 分卷剧情。
- 阶段目标。
- 人物成长轨迹。

第三层：章节记忆

- 章节摘要。
- 关键事件。
- 人物状态变化。
- 新增事实。

第四层：动态检索记忆

- 根据当前章节内容检索相关人物。
- 检索历史事件。
- 检索相关伏笔。
- 检索相关地点、物品和事实。
- 只向 AI 提供当前写作真正需要的上下文。

### 5. AI 写作质量控制

- 

  增加章节目标完成度检查。

- 

  增加人物行为合理性检查。

- 

  增加剧情逻辑检查。

- 

  增加时间线检查。

- 

  增加文风一致性检查。

- 

  增加重复情节检测。

- 

  增加章节质量评分。

- 

  AI 修改章节前保留原稿。

- 

  AI 修改后展示修改内容和修改原因。

- 

  不允许 AI 在没有确认的情况下擅自修改核心世界观和人物设定。

## 五、第四阶段：代码架构优化（P1）

### 1. 模块解耦

建议将代码组织为：

lib/

- db/
  - database.ts
  - schema.ts
  - migrations/
- repositories/
  - project.repository.ts
  - chapter.repository.ts
  - character.repository.ts
  - canon.repository.ts
  - job.repository.ts
- services/
  - project.service.ts
  - chapter.service.ts
  - version.service.ts
- agents/
  - architect.agent.ts
  - writer.agent.ts
  - reviewer.agent.ts
- pipeline/
  - pipeline.ts
- publishers/
  - fanqie.ts

要求：

- 

  Agent 不直接承担数据库和文件读写职责。

- 

  统一通过 Repository 访问数据。

- 

  统一通过 Service 处理业务逻辑。

- 

  统一错误处理和日志系统。

- 

  使用 Zod 等工具校验 AI 返回的数据。

- 

  统一任务状态机。

- 

  避免重复代码和重复业务逻辑。

### 2. 测试体系

- 

  增加核心模块单元测试。

- 

  增加数据库集成测试。

- 

  增加任务并发测试。

- 

  增加章节生成测试。

- 

  增加台账重建测试。

- 

  增加章节版本恢复测试。

- 

  增加服务重启恢复测试。

- 

  增加完整写作流程 E2E 测试。

## 七、第六阶段：安全性与发布功能（P2）

- 

  API Key 不得暴露在前端和普通日志中。

- 

  所有 API 参数进行校验。

- 

  防止文件路径穿越。

- 

  重要删除操作增加确认。

- 

  浏览器 Cookie 和登录会话安全存储。

- 

  发布前支持内容预览。

-

-

-

- 

  保存发布失败截图和错误日志。

## 八、开发执行要求

请按照以下顺序实施：

第一步：完整检查现有代码，确认以上问题是否真实存在，不要直接假设所有问题都存在。

第二步：输出详细的代码审查报告，列出涉及的文件、函数、问题原因和修复方案。

第三步：优先完成第一阶段的 P0 问题。

第四步：完成 SQLite 数据库改造，保证旧项目数据可以安全迁移。

第五步：完成剧情事件、人物状态、伏笔和长篇记忆系统。

第六步：完成代码架构优化、测试和前端功能完善。

每完成一个阶段，都必须：

1. 执行 TypeScript 类型检查。
2. 执行 ESLint。
3. 执行相关单元测试和集成测试。
4. 检查现有功能是否受到影响。
5. 更新项目文档。
6. 汇报修改文件、修改内容、测试结果和遗留问题。

特别注意：

- 不要一次性重写整个项目。
- 不要为了引入数据库而删除现有 Markdown 文件功能。
- 不要擅自更换现有模型供应商和 API 接口。
- 不要擅自修改现有用户配置。
- 不要在没有备份的情况下执行数据迁移。
- 不要用模拟测试结果代替真实测试。
- 如果发现现有架构与改造方案冲突，先说明原因，再提出兼容方案。

## 九、最终验收标准

项目改造完成后，应满足：

1. 多个小说项目之间的数据完全隔离。
2. 服务异常退出不会导致小说正文或事实台账损坏。
3. 同一个项目不会出现冲突任务同时执行。
4. 所有章节都能够查看和恢复历史版本。
5. AI 能够结合全书剧情、人物状态和伏笔进行创作。
6. AI 不能在事实抽取失败时错误通过章节审校。
7. 数据库和 Markdown 文件能够正常备份、恢复和迁移。
8. 现有写作、审校、重写和发布功能正常运行。
9. 核心业务逻辑拥有可重复执行的自动化测试。

**最终目标：将 Quillmate-AIWriter 打造成一个稳定、可靠、支持长篇小说持续创作的 AI 写作平台。**
