# Quillmate-AIWriter 第二阶段优化与升级清单

项目地址：https://github.com/L-jiemoo/Quillmate-AIWriter

## 一、项目改造目标

本次改造以当前 GitHub main 分支的实际源码为基础，不重新开发已经完成的功能，而是在现有架构上继续完善。

本次升级的核心目标：

1. 提高小说生成流水线的稳定性。
2. 防止小说正文、事实台账和发布记录出现错误。
3. 完善多文件数据一致性和版本管理。
4. 建立真正适合长篇小说的记忆系统。
5. 增强人物状态、剧情事件和伏笔管理能力。
6. 完善自动化测试和代码质量管理。
7. 提高项目的安全性和可维护性。

最终目标是将项目升级为一个能够长期管理长篇小说创作过程的 AI 小说创作工作台。

## 二、改造前必须遵守的要求

### 1. 先检查现有代码

开始修改前，必须重新检查 GitHub 当前 main 分支。

不能仅根据 README、项目说明或之前的分析结果直接修改。

必须检查：

- 实际源码。
- 函数调用关系。
- API 路由。
- 数据读写逻辑。
- 异常处理。
- 现有测试。
- 相关功能之间的依赖关系。

### 2. 不要重复开发已有功能

以下功能已经有一定实现，不要推倒重做：

- JSON 异常处理。
- 文件原子写入。
- 文件备份。
- 项目级任务锁。
- 任务持久化与恢复。
- 任务取消和重试。
- 项目完整性检查。
- Vitest。
- ESLint。
- 基础事实台账。
- 基础人物状态记录。
- 番茄小说发布适配器。

如果发现现有实现存在缺陷，应在原有基础上修复和完善。

### 3. 修改前输出审查报告

针对每个改造项目，先说明：

- 当前实现情况。
- 涉及的文件和函数。
- 目前存在的问题。
- 修改方案。
- 对其他功能的影响。
- 数据迁移风险。
- 对现有项目的兼容性。

未经确认，不要擅自大规模重构。

## 三、第一阶段：修复核心数据可靠性问题（P0）

### 任务 1：事实抽取失败必须阻断章节通过

涉及文件：lib/pipeline.ts

当前问题：

事实抽取失败后，程序仍可能使用空对象继续执行审校，导致未经完整事实检查的章节有机会通过。

改造要求：

1. 事实抽取失败后，章节不能被标记为正式审校通过。
2. 增加事实抽取失败状态。
3. 支持有限次数自动重试。
4. 超过重试次数后进入待复查状态。
5. 不允许失败的抽取结果覆盖原有事实数据。
6. 保留章节草稿，避免正文丢失。
7. 在任务日志中明确记录失败原因。
8. 前端明确展示失败状态和重试入口。

验收标准：

- 正常抽取时可以正常审校。
- 抽取失败时不能误通过。
- 重试成功后可以继续执行。
- 多次失败后可以人工处理。
- 不会因为抽取失败而丢失原有正文。

### 任务 2：事实台账改为安全的整体重建机制

涉及文件：lib/pipeline.ts、lib/store.ts，以及相关事实台账模块。

当前问题：

runRecanon() 目前逐章抽取、逐章保存，可能出现部分章节失败，但正式台账已经被部分更新的情况。

改造要求：

1. 重建时创建独立的临时台账。
2. 逐章抽取事实，不直接修改正式台账。
3. 记录每章的处理状态。
4. 记录失败章节及失败原因。
5. 对最终台账执行完整性检查。
6. 全部成功并通过校验后，才统一替换正式台账。
7. 如果任何关键步骤失败，保留原台账。
8. 支持失败后重新执行。
9. 提供重建进度和失败详情。

验收标准：

- 重建成功后正式台账完整更新。
- 中途失败时旧台账保持不变。
- 不能把部分成功误报为完整成功。
- 支持从失败状态恢复或重新执行。

### 任务 3：发布记录与永久去重记录分离

涉及文件：lib/store.ts、lib/pipeline.ts、lib/publishers/fanqie.ts。

当前问题：

发布历史存在最多保留 100 条的限制，可能导致早期成功发布记录被清理，进而影响重复发布判断。

改造要求：

1. 将发布操作日志与永久发布状态分开。
2. 日志允许按策略清理。
3. 永久发布状态不能因为日志清理而丢失。
4. 使用平台 ID、作品 ID、章节编号建立唯一发布标识。
5. 发布前检查该章节是否已经成功发布。
6. 支持发布失败后的恢复。
7. 对不确定是否成功的发布操作增加人工确认机制。
8. 清理历史日志时不能清理永久去重记录。
9. 对已有发布记录进行兼容迁移。

验收标准：

- 已成功发布的章节不会因为日志清理而重复发布。
- 同一章节重复执行发布任务时能够正确识别。
- 发布失败时可以恢复。
- 不能将状态不明的章节直接判定为发布成功。

## 四、第二阶段：数据一致性和版本管理（P1）

### 任务 4：架构生成统一提交

涉及文件：lib/pipeline.ts、lib/store.ts。

当前问题：

大纲、世界观和人物卡可能分批保存，导致部分生成成功、部分生成失败时出现数据不一致。

改造要求：

1. 大纲生成完成后先暂存。
2. 世界观生成完成后先暂存。
3. 人物卡生成完成后先暂存。
4. 对所有生成结果执行校验。
5. 全部通过后再统一提交。
6. 中途失败时不覆盖原有完整项目资料。
7. 保留用户手动编辑过的人物资料。
8. 提供失败恢复机制。

验收标准：

- 生成成功后相关资料保持一致。
- 中途失败时原有资料不丢失。
- 不会意外覆盖用户手动编辑的内容。

### 任务 5：大纲多文件一致性保护

涉及文件：lib/pipeline.ts、lib/store.ts。

需要保护的文件：

- plan.json
- outline.md
- 项目元数据。

改造要求：

1. 多个文件更新前先生成备份。
2. 使用统一提交流程。
3. 任何关键步骤失败时能够回滚。
4. 提供文件一致性检查。
5. 支持自动修复能够确定的文件不一致问题。
6. 无法自动修复时提示用户，不允许静默覆盖。

验收标准：

- 不会出现章节细纲已经增加但主线大纲没有同步的情况。
- 异常中断后可以恢复。
- 不会破坏用户原有大纲。

### 任务 6：严格章节编号校验

改造要求：

在生成和保存大纲时执行严格检查：

- 不允许重复章节编号。
- 不允许负数和零。
- 不允许小数编号，除非项目明确支持特殊章节。
- 不允许意外断号。
- 不允许超出目标章节数量。
- 不允许空标题。
- 不允许空摘要。
- 检查章节顺序。
- 检查章节数量与项目目标是否一致。

验收标准：

生成错误的大纲时，应在保存前拦截，并明确提示错误位置。

### 任务 7：章节版本管理

当前文件备份不能完全替代章节版本管理。

改造要求：

1. 每次正式修改章节正文时创建版本记录。
2. 记录版本编号、创建时间和修改来源。
3. 记录修改前后的正文。
4. 支持查看历史版本。
5. 支持版本差异对比。
6. 支持恢复到指定版本。
7. AI 重写章节时不能直接销毁旧版本。
8. 区分 AI 修改、用户手动修改和系统修复。

验收标准：

- 任意章节可以查看历史版本。
- 可以恢复指定版本。
- 版本恢复不会覆盖其他章节。
- 版本记录可以持久保存。

## 五、第三阶段：SQLite 数据库升级（P1）

### 任务 8：引入 SQLite 结构化数据管理

不要将所有小说正文强行放入数据库。

建议采用 SQLite + Markdown 混合架构。

SQLite 负责：

- 项目元数据。
- 章节元数据。
- 人物资料。
- 人物状态。
- 人物关系。
- 事实台账。
- 剧情事件。
- 伏笔记录。
- 任务状态。
- 任务日志。
- 章节版本信息。
- 审校记录。
- 发布状态。
- AI 模型配置。

Markdown 负责：

- 小说章节正文。
- 世界观文档。
- 大纲文档。
- 其他长文本创作资料。
- 导入和导出内容。

建议数据库表：

- projects
- chapters
- characters
- character_states
- character_relationships
- canon_facts
- plot_events
- foreshadows
- jobs
- job_logs
- chapter_versions
- reviews
- publish_records
- model_configs

具体表结构应根据现有数据模型设计，不要为了符合表名而重复存储同一份数据。

### 数据库改造要求

1. 先设计数据库 Schema。
2. 增加数据库访问层。
3. 增加 Repository 数据访问层。
4. 使用事务处理关联数据更新。
5. 增加数据库迁移机制。
6. 支持数据库备份和恢复。
7. 提供现有 JSON 数据迁移工具。
8. 保留 Markdown 正文文件。
9. 保留现有数据导入和导出能力。
10. 提供迁移前后数据数量和内容校验。
11. 迁移失败时能够回滚。
12. 不允许在没有备份的情况下执行破坏性迁移。

### 验收标准

- 现有小说项目可以正常读取。
- 现有章节正文不丢失。
- 人物和事实台账可以正确迁移。
- 数据库事务能够正常回滚。
- 旧数据可以备份和恢复。
- 迁移完成后原有功能正常运行。

## 六、第四阶段：长篇小说分层记忆系统（P1）

这是本次升级最重要的创作能力建设之一。

### 任务 9：建立分层记忆系统

目前不能只依赖最近几章摘要作为 AI 的写作上下文。

建议建立四层记忆：

#### 第一层：全书记忆

保存：

- 世界观。
- 核心设定。
- 故事主线。
- 核心人物。
- 重要规则。
- 故事最终目标。
- 全书关键矛盾。

#### 第二层：分卷记忆

保存：

- 每卷剧情目标。
- 本卷主要事件。
- 人物阶段性变化。
- 本卷主要冲突。
- 本卷重要伏笔。
- 与其他卷的联系。

#### 第三层：章节记忆

保存：

- 章节摘要。
- 发生的事件。
- 出场人物。
- 人物行动。
- 时间和地点。
- 章节结尾状态。
- 新增设定。
- 新增伏笔。

#### 第四层：动态检索记忆

AI 写作前，根据当前章节内容自动检索：

- 相关人物资料。
- 相关历史事件。
- 相关世界观规则。
- 相关历史章节。
- 相关伏笔。
- 相关人物关系。
- 相关时间线。

不需要每次把整本小说都发送给模型。

### 任务 10：建立记忆检索机制

改造要求：

1. 根据当前章节大纲识别相关人物。
2. 根据剧情关键词检索相关历史事件。
3. 根据人物 ID 查询人物历史状态。
4. 根据事件 ID 查询关联章节。
5. 检索相关世界观规则。
6. 检索未回收伏笔。
7. 将检索结果整理为结构化上下文。
8. 对上下文设置合理的 Token 预算。
9. 重要事实应有来源记录。
10. 检索不到资料时不能自行编造为既定事实。

### 任务 11：记忆更新机制

改造要求：

- 新章节完成后自动生成章节记忆。
- 新事件自动进入事件记录。
- 人物状态变化后更新人物状态。
- 新增设定进入事实台账。
- 重要剧情进入分卷和全书摘要。
- 支持人工修改和纠正 AI 生成的记忆。
- 记忆更新失败不能破坏已有记忆。

验收标准：

AI 在写作新章节时，能够根据剧情自动检索相关历史信息，而不是只依赖最近几章摘要。

## 七、第五阶段：人物状态、剧情事件和伏笔系统（P1/P2）

### 任务 12：人物状态追踪

不能只保存静态人物卡。

需要记录人物在故事推进过程中的动态变化：

- 当前身份。
- 年龄或故事时间对应年龄。
- 当前所在位置。
- 身体状态。
- 生死状态。
- 能力变化。
- 人物目标。
- 当前掌握的信息。
- 人物关系。
- 所属阵营。
- 重要经历。

要求：

1. 人物状态具有历史记录。
2. 状态变化关联对应剧情事件。
3. 支持查询某一时间点的人物状态。
4. 检查人物行为是否符合当前状态。
5. 检查死亡人物是否被错误地安排在后续剧情中。
6. 允许合理的剧情解释，例如复活、假死和身份伪装，但必须有对应事件依据。

### 任务 13：剧情事件系统

建立独立的剧情事件记录。

每个事件至少包括：

- 事件 ID。
- 事件名称。
- 发生时间。
- 发生地点。
- 参与人物。
- 事件起因。
- 事件过程。
- 事件结果。
- 关联章节。
- 对后续剧情的影响。

要求：

1. 事件之间可以建立关联。
2. 支持事件时间线查询。
3. 支持人物事件历史查询。
4. 支持事件因果关系追踪。
5. 检查时间线冲突。
6. 检查人物是否在不合理的时间出现在不同地点。

### 任务 14：伏笔追踪系统

每条伏笔至少包括：

- 伏笔 ID。
- 伏笔内容。
- 埋设章节。
- 相关人物。
- 预计回收章节或范围。
- 当前状态。
- 关联事件。
- 回收说明。

伏笔状态：

- 已埋设。
- 发展中。
- 待回收。
- 已回收。
- 已废弃。

要求：

1. AI 写作时能够检索相关伏笔。
2. 避免重复埋设相同伏笔。
3. 对长期未回收的伏笔进行提醒。
4. 回收时记录对应章节。
5. 允许作者手动修改伏笔状态。
6. 不允许 AI 擅自将重要伏笔判定为已回收。

## 八、第六阶段：AI 创作质量控制（P1/P2）

### 任务 15：AI 提示词版本管理

改造要求：

1. 记录不同 Agent 使用的提示词版本。
2. 修改提示词后能够查看历史版本。
3. 支持回滚到旧版本。
4. 记录模型、参数和提示词版本。
5. 建立典型小说场景测试集。
6. 对不同提示词版本进行回归测试。

### 任务 16：增强章节审校能力

建议增加以下检查维度：

- 人物行为合理性。
- 人物性格一致性。
- 时间线连续性。
- 地点连续性。
- 人物生死状态。
- 物品归属。
- 世界观规则冲突。
- 剧情因果关系。
- 伏笔连续性。
- 章节内容重复。
- 章节与大纲偏离程度。

要求：

1. 审校结果应给出具体证据。
2. 尽量关联具体章节和原文位置。
3. 区分严重错误和一般建议。
4. 不允许 AI 为了通过审校而擅自修改既定剧情。
5. 支持定点修复。
6. 修复后重新执行相关检查。
7. 保留修复前版本。

## 九、第七阶段：工程质量和安全（P2）

### 任务 17：完善自动化测试

项目已经接入 Vitest 和 ESLint，不需要重复安装。

需要进一步完善：

- 核心业务单元测试。
- 数据库事务测试。
- 文件读写测试。
- 任务并发测试。
- 任务恢复测试。
- 事实台账测试。
- 记忆检索测试。
- 发布去重测试。
- API 路由测试。
- 关键创作流程集成测试。

要求：

1. 测试失败时不能静默通过。
2. 不能使用纯 Mock 测试冒充真实集成测试。
3. AI API 测试应区分 Mock 测试和真实模型测试。
4. 关键数据处理模块必须有失败场景测试。
5. 增加测试覆盖率报告。

### 任务 18：GitHub Actions

建立自动化检查流程。

每次提交或 Pull Request 时自动执行：

1. npm install 或 npm ci。
2. ESLint。
3. TypeScript 类型检查。
4. Vitest。
5. Next.js Build。

任何关键检查失败时，不应将该次提交标记为通过。

### 任务 19：API 和安全性检查

改造要求：

- 统一 API 运行时参数校验。
- 防止路径穿越。
- 保护 API Key。
- 改进敏感配置存储。
- 限制危险文件操作。
- 删除操作增加二次确认。
- 发布操作增加安全检查。
- 对异常信息进行适当脱敏。
- 对任务接口增加必要的权限和并发控制。

### 任务 20：发布适配器回归测试

针对番茄小说发布功能：

1. 检查登录状态。
2. 检查作品选择。
3. 检查章节选择。
4. 检查正文输入。
5. 检查发布结果。
6. 检查重复提交。
7. 检查网络异常。
8. 检查发布失败恢复。
9. 检查登录失效。
10. 检查平台页面结构变化。

## 十、开发执行顺序
